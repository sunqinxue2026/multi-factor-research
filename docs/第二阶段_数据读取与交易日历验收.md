## 1. 本阶段目标

建立兼容项目一八列日频行情格式的多股票数据层，为后续按股票回看、按日期进行横截面研究提供明确的数据契约。

验收目标：

1. 批量读取多股票CSV，保留股票代码前导零。
2. 检查字段、日期、股票与日期联合键、数值及OHLC价格关系。
3. 明确记录来源、复权口径、单位、数据截至日期和样本覆盖限制。
4. 使用显式市场交易日历对齐日期，不以普通工作日或已有报价反推交易日历。
5. 区分真实零值、字段缺失、整条记录缺失及未知市场状态，不自动填充价格或推断停牌。
6. 提供单日横截面查询和可追溯的命令行输出。
7. 通过手工数据验证具体数值、错误输入、状态边界与历史不变性。

本阶段不实现因子、预处理、未来收益标签、IC、分组、组合、数据库写入或回测适配，不复制项目一回测引擎。

## 3. 已实现的功能

### 3.1 行情数据契约

标准输入：

```csv
symbol,trade_date,open,high,low,close,volume,amount
```

| 字段／规则 | 实际行为 |
|---|---|
| 股票代码 | CSV按字符串读取，非空且不允许首尾空格，保留前导零 |
| 日期 | 严格要求YYYY-MM-DD，并检查日期真实存在 |
| 联合键 | `(symbol, trade_date)`唯一；完全相同的重复行也拒绝 |
| 价格 | 有效值必须为正，允许真实缺失 |
| 成交量、成交额 | 有效值非负；0和缺失保持区别 |
| 非法输入 | 非法字符串、无穷数、布尔数值拒绝 |
| OHLC | 检查low≤open/close≤high及low≤high；缺失不自动修补 |
| 输出 | 只保留八个标准字段，按股票、日期排序，使用副本不原地修改输入 |

### 3.2 来源、日历与面板

- `DatasetMetadata`检查来源、市场、覆盖说明、数据截至日期、合成标记、复权口径和单位；当前仅接受CNY／股／CNY，不自动换算。
- `read_market_csv()`用同一份文件字节解析并计算SHA-256，记录文件名及摘要。
- `TradingCalendar`要求非空、日期唯一，排序后使用；CSV只能包含`trade_date`一列。
- 行情与日历市场必须相同，行情必须属于日历，行情和日历不能晚于`data_as_of`。
- `build_calendar_panel()`生成全部已观察股票×给定交易日的网格，补齐日期位置，但不补行情。
- `cross_section()`提取某天的股票横截面副本，调用者修改返回值不影响原面板。

### 3.3 状态字段与含义

| 字段 | 实际含义 |
|---|---|
| `observed` | 输入中是否存在该股票日期记录 |
| `price_complete` | OHLC是否齐全，不表示能够成交 |
| `is_listed` | 逐日上市事实；没有资料时为未知 |
| `is_suspended` | 逐日停牌事实；不根据零成交或缺行情推断 |
| `tradable` | 缺价、明确停牌或明确未上市时为False，其余未知；当前没有True分支 |
| `status_reason` | 一个主要原因，不是所有问题的完整列表 |

原因优先级按实际覆盖赋值顺序为：明确未上市＞明确停牌＞缺少记录＞缺少价格＞执行条件未知。

可选状态表只允许联合键及`is_listed`、`is_suspended`；重复键、面板外键、非布尔非空状态及额外字段会被拒绝。状态只作用于给定日期，不向其他日期传播。

### 3.4 正式运行入口

```text
CSV＋来源JSON＋日历CSV
→ 来源校验和行情读取
→ 市场、日期及联合键检查
→ 日历面板和状态构建
→ panel.csv＋summary.json
```

摘要记录数量、元数据、行情和日历摘要、日历版本、UTC开始时间、耗时、Python／Pandas版本及限制。输出目录已存在时拒绝覆盖；先写面板再写摘要，不是文件事务，失败可能留下部分产物。

## 5. 核心数据结构、算法和公式

### 5.1 数据结构与接口

| 结构／函数 | 输入输出和职责 |
|---|---|
| `DatasetMetadata` | 来源、市场、复权、单位、截至日期及股票覆盖声明 |
| `MarketDataset` | 行情DataFrame＋元数据＋原文件摘要和文件名 |
| `TradingCalendar` | 排序、唯一的DatetimeIndex及来源和版本 |
| `PanelResult` | 对齐面板及元数据、日历信息、行情摘要 |
| `validate_market_frame()` | 原始DataFrame→已校验、排序的八列副本 |
| `read_market_csv()` | CSV路径＋元数据→MarketDataset |
| `build_calendar_panel()` | 行情＋日历＋可选逐日状态→PanelResult |
| `PanelResult.cross_section()` | 日期→当日股票数据副本 |

数据类和类型注解不等于全部对象不可变。行情DataFrame仍可变，面板构建会重新校验输入；`DatasetMetadata`的冻结也不代表整个系统不可变。

### 5.2 核心对齐算法

实际代码使用：

```python
index = pd.MultiIndex.from_product(
    [sorted(frame.symbol.unique()), calendar.dates], names=KEYS
)
observed = frame.set_index(KEYS)
panel = observed.reindex(index)
```

设股票集合S、日历集合T，完整面板的键为笛卡尔积S×T；`reindex()`为缺少的键添加空值，不产生虚构报价。`index.isin(observed.index)`生成`observed`。

OHLC完整性为四个价格都非空。阻止执行的逻辑为：

```text
缺少任一OHLC价格 OR 明确停牌 OR 明确未上市
```

没有阻止条件时仍为未知，不推导为可以成交。行情摘要由原CSV字节的SHA-256计算；不涉及收益、因子或绩效公式。

### 5.3 复杂度

设输入M条、股票S只、日历T天，P＝S×T。

| 操作 | 规模估计 |
|---|---|
| 固定字段校验 | O(M) |
| 股票日期排序 | O(M log M) |
| 网格和对齐 | 通常约O(M＋P)，另有索引开销 |
| 面板空间 | O(P)，副本和中间对象提高峰值内存 |
| 当前横截面查询 | 扫描约O(P)，另外复制当日结果 |
| 文件读取 | 原始字节与解析后的表同时占内存 |

以上是算法分析，不是性能测试结果。

## 6. 采用该方案的原因

1. **行情与日历分离：** 某天没有报价不代表市场休市，不能用行情自身生成完整开放日历。
2. **先校验后对齐：** 重复键、错误数值必须先暴露，避免索引歧义和污染后续研究。
3. **补位置而非补价格：** 删除缺口会让跨多个交易日的价格变化被误作单日日收益；当前保留位置供后续窗口检查。
4. **区分未知和False：** 没有上市／停牌证据不能自动标否，更不能保证成交。
5. **数据与入口分层：** 业务逻辑不依赖命令行，方便测试、复用及后续研究入口接入。
6. **追溯而不夸大：** 来源说明、日历版本和文件摘要用于解释输入身份，不冒充真实性认证或历史可获得性证明。
7. **优先可解释性：** 当前完整长表便于逐股票检查时间序列，也便于提取同日横截面。

## 7. 可选替代方案

| 方案 | 优点 | 取舍与当前未采用原因 |
|---|---|---|
| 稀疏长表 | 缺失较多时更省内存 | 必须另行检查市场日间隔，不能直接按记录数滚动 |
| 日期×股票宽表 | 适合部分向量化收益计算 | 多字段、状态和来源组织不如长表直接 |
| 按股票分块 | 控制峰值内存 | 同日横截面需要重新汇总 |
| 数据库按需查询 | 控制读取范围并支持索引 | 需要连接、版本和一致性设计；第二阶段尚无数据库层 |
| 日期索引或分区 | 加快重复截面查询 | 需实测确认收益，维护额外索引有成本 |
| 独立估值价格序列 | 可以明确支持停牌期间沿用旧价格估值 | 必须与研究价格、成交价格分开；当前未实现此规则 |

替代方案不能默认改变缺失和交易语义。若后续涉及重要技术决策，先解释影响并等待负责人确认。

## 8. 性能瓶颈和后续优化方向

### 8.1 当前可能的瓶颈

- 股票×日历完整展开，在股票多、历史长且缺失多时占用内存。
- CSV原始字节、原表、校验副本和面板同时存在，提高峰值内存。
- `build_calendar_panel()`重新校验，存在重复处理成本，但提供API防御检查。
- `cross_section()`目前全表过滤，重复访问多个日期可能反复扫描。
- CSV全量解析和文本导出不适合无限扩大数据规模。

### 8.2 后续优化顺序

1. 先在明确数据规模上测量读取、校验、对齐、截面查询耗时和峰值内存。
2. 根据结果考虑日期索引、分块或稀疏存储，不先承诺加速倍数。
3. 在保持联合键、缺口和状态语义的前提下优化，保留现有数值回归测试。
4. 输入快照与输出一致性属于可靠性改进，应与纯性能优化分开设计。

本阶段未开展规模性能基准；极小样例耗时不能外推全市场吞吐量。

## 9. 面试官可能追问的问题及回答思路

### 9.1 为什么不能删除缺失行后直接计算收益？

结合`MultiIndex.from_product()`和`reindex()`说明：相邻有效记录可能跨多个开放日。完整面板保留缺口，下一阶段必须检查连续窗口，不能仅按剩余记录数滚动。

### 9.2 为什么不前向填充停牌价格？

估值、研究和执行价格用途不同。当前模块不把沿用价伪装成新报价；停牌还需要外部逐日事实，零成交和缺记录不构成证明。

### 9.3 时间序列和横截面有什么不同？

同一股票沿日期回看是时间序列；`cross_section()`取得同一天多只股票，是横截面。后续因子按股票计算，标准化和排名按日期比较。当前没有实现这些统计。

### 9.4 如何证明没有修改调用者数据？

校验选择标准列后深复制，截面也返回副本。`test_alignment_exact_values_and_no_fill`既比较原始输入，也修改截面验证原面板不变。DataFrame仍可变，不能宣称完全不可变架构。

### 9.5 为什么报价齐全，tradable仍不是True？

`price_complete`只证明字段存在；涨跌停、停牌、数量约束和撮合条件未完整建模。数据层只表达已知阻止条件，其余保留未知。

### 9.6 SHA-256证明了什么？

`read_market_csv()`用同一字节计算摘要并解析，标识本次输入文件；不证明数据真实、授权完整、正确复权或历史时点可获得。当前摘要测试只核对长度，仍有独立预期值测试的改进空间。

### 9.7 追加未来数据测试是否消除了未来泄漏？

不是。现有测试覆盖同一已观察股票集合下历史面板不变。未来新增股票会扩展历史网格；时点股票池、标签和因子窗口仍需后续独立设计和测试。

### 9.8 如何处理幸存者偏差？

当前股票集合取自输入，缺少完整历史股票池和退市样本，不能消除偏差。来源说明和报告必须披露覆盖限制，不能用全样本集合冒充历史可投资股票池。

### 9.9 Python 3.10兼容性如何证明？
